## 1. 核心概念 (Core Concepts)

**MQTT（Message Queuing Telemetry Transport，訊息佇列遙測傳輸協定）** 是由 IBM 於 1999 年設計的一種極度輕量、基於 TCP/IP 協定的發布／訂閱（Publish/Subscribe）訊息通訊機制。

在物聯網（IoT）場景中，硬體裝置往往具有運算資源有限、電池供電、或是處於蜂巢式行動網路頻寬受限、延遲較高的惡劣環境。傳統網頁常用的 **HTTP 協定** 採用「請求／回應（Request/Response）」模式，每次連線都必須重新握手並夾帶龐大的 Header 標頭資訊（通常達數百 Byte 至數 KB），造成嚴重的電力消耗與頻寬浪費。

相較之下，**MQTT 固定標頭僅有 2 個 Bytes**，並具備長連線保持（Keep-Alive）特性，因此成為物聯網工業界公認的通訊標準。

## 2. Publish / Subscribe（發布與訂閱）運作架構

MQTT 徹底打破了傳統客戶端與伺服器之間「一對一固定連線」的依賴關係，透過**完全解耦（Decoupling）**的設計運作：

```
+-------------------------------------------------------------------------+
|                        MQTT 發布與訂閱架構圖                            |
|                                                                         |
|  [發布者 Publisher]                                                     |
|    ESP32 感測節點 ──▶ 發送至 Topic: "lab/roomA/env" ──┐                 |
|                                                      ▼                  |
|                                            +------------------+         |
|                                            |   MQTT Broker    |         |
|                                            | (Mosquitto/EMQX) |         |
|                                            +------------------+         |
|                                                      │                  |
|               ┌──────────────────────────────────────┴───────────────┐  |
|               ▼                                                      ▼  |
|      [訂閱者 Subscriber 1]                                 [訂閱者 Subscriber 2] |
|       前端網頁 (Web Dashboard)                                Raspberry Pi 閘道器 |
|   (訂閱 "lab/+/env"，即時畫圖)                             (訂閱 "lab/#"，存資料庫) |
+-------------------------------------------------------------------------+
```

### 2.1 三大核心角色分工
1. **Publisher（發布者）**：
   資料的產生端（例如我們的 ESP32 感測板）。它只負責將封裝好的訊息（Payload）推送給特定的 **主題（Topic）**，它**完全不需要知道有誰在接收、或者是否有任何人在線**。
2. **Subscriber（訂閱者）**：
   資料的消費者（例如使用者的瀏覽器網頁儀表板、手機 App、或是負責記錄資料庫的伺服器）。它向 Broker 登記自己有興趣的 Topic，只要該主題有任何新資料進來，Broker 就會主動推播（Push）給它。
3. **Broker（訊息代理人／轉運站）**：
   整個系統的核心樞紐（如開源的 Eclipse Mosquitto 或 EMQX）。負責管理所有用戶端連線、過濾主題、並以極低延遲將訊息準確分發給所有合法訂閱者。

## 3. 主題路徑 (Topic) 與萬用字元設計

MQTT 的主題採用階層式命名架構，以正斜線 `/` 區隔層級，例如：
`ncut/csie/lab502/pm25`

### 支援的萬用字元 (Wildcards)：
- **單層萬用字元 `+`**：
  代表該層級的任意單一名稱。  
  例如：`ncut/csie/+/pm25` 可以同時接收 `lab502` 與 `lab503` 的 PM2.5 數據，但不會匹配多層路徑。
- **多層萬用字元 `#`**：
  代表該層級以下的所有子主題，必須放在主題最後一個字元。  
  例如：`ncut/csie/lab502/#` 可以一次接收該實驗室的所有感測器（pm25、temperature、humidity、fan_status）資訊。

## 4. QoS 服務品質等級 (Quality of Service)

| QoS 等級 | 運作機制 | 頻寬負擔 | 適用情境 |
| :--- | :--- | :--- | :--- |
| **QoS 0** (最多送達一次) | Best-effort 射後不理，無 ACK 確認 | 最低 (標頭最小) | 高頻率環境採樣 (如每秒更新 PM2.5，掉一筆無妨) |
| **QoS 1** (至少送達一次) | 需 PubAck 回應，若超時則重發 (可能重複) | 中等 | 關鍵警報通知 (如濾網異常更換通知) |
| **QoS 2** (剛好送達一次) | 經過四次握手確認，保證絕不遺失且絕不重複 | 最高 | 財務扣款、精密機台啟動訊號 |

## 5. 新手生活化比喻 (Novice Analogy)

> 💡 **就像 YouTube 頻道與訂閱按鈕**：  
> - **發布者（Publisher = YouTuber）**：創作者拍好影片後，直接上傳到自己的頻道（Topic）。他不用逐一打電話通知 50 萬名粉絲「我發片囉！」。  
> - **Broker（YouTube 雲端伺服器平台）**：平台負責維護整個頻道的內容庫與龐大的追隨者名單。  
> - **訂閱者（Subscriber = 開啟小鈴鐺的觀眾）**：你只要按下訂閱某頻道，一旦有新影片發布，平台伺服器就會「主動跳出推播通知」送到你的手機螢幕上。
